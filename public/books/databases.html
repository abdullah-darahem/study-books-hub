Introduction to DBMSs

What a database and a DBMS are, why an operating system cannot manage databases, data models, the three levels of data description, the people who work with DBMSs, DDL & DML, integrity constraints, the structure of a DBMS, and client–server architectures.

يعني إيه Database و DBMS؟ وليه الـ Operating System مينفعش يدير قواعد البيانات؟ وبعدين الـ data models، والـ ٣ مستويات، والناس اللي بتشتغل مع الـ DBMS، ولغات DDL و DML، والـ integrity constraints، ومكونات الـ DBMS من جوه، والـ architectures.

1.1

Databases, DBMSs & Why Not the OS

يعني إيه Database و DBMS، وليه مش الـ OS؟

Database: an organized collection of data that describes the activities of an organization (or a group of related organizations). In short: a collection of entities and the relationships between them.

DBMS (Database Management System): software — a group of programs working as one unit — used to manage and maintain databases.

Operating System: software that governs a Computer System, which comprises Hardware, Users, and Applications.

A DBMS must be…Meaning
Fastvery fast in every user operation
Integrablekeeps data integrity & consistency after any operation
Securegives each user group only the data its permissions allow

Why the OS fails with databases (DB files reach TBs; many users at once):

  1. The OS transfers the entire file into RAM — impossible for TB files with GB memory.
  2. The OS secures data with a password only — not flexible enough for per-group permissions.
  3. The OS needs a special program (script) for every question a user asks — complex for huge data.
Operating SystemDBMS
A file is…a string of charactersa collection of pages, each page a collection of records
Loadsthe whole fileonly the needed pages
Asking questionswrite a script each timeSQL

Extra DBMS benefits: data independence, libraries of functions for building new applications, and efficient interfaces → short application development time.

عالشرح بالعربيالفكرة اللي المادة كلها مبنية عليها
  • الـ Database = بيانات منظمة بتوصف شغل مؤسسة. مثال الكتاب (الجامعة): الـ entities هي الطلبة والدكاترة والكورسات والقاعات، والـ relationships هي علاقة الطالب بالكورس، والدكتور بالكورس، والكورس بالقاعة.
  • الـ DBMS = البرنامج اللي بيدير الـ database ويحافظ عليها. خلي بالك: الـ DBMS software مش hardware.
  • الـ Computer System بيتكوّن من ٣ حاجات: Hardware و Users و Applications — وده سؤال «أكمل» مشهور.
  • الـ DBMS لازم يبقى: سريع (Fast)، ومحافظ على صحة البيانات (Integrable)، وآمن (Secure). سؤال Mid 2026: «أنهي واحدة مش صفة مطلوبة؟» ← Unstructured.
  • ليه الـ OS مينفعش؟ ٣ مشاكل: (١) بينقل الملف كله للـ RAM — والملف ممكن يبقى terabytes والميموري gigabytes. (٢) الحماية بـ password بس — مفيش صلاحيات مختلفة لكل مجموعة. (٣) لازم تكتب script لكل سؤال.
  • الحل في الـ DBMS: الملف بقى مجموعة pages (وكل page فيها records)، فبينقل للميموري الصفحات اللي محتاجها بس. ولكل الأسئلة اخترعوا لغة واحدة: SQL.
فخ متكرر: «The view of file is the same in OS and DBMS» ← False. الـ OS شايف الملف string of characters، والـ DBMS شايفه collection of pages.
فخ تاني: «Operating Systems is classified as a hardware system» ← False — الـ OS ده software.
1.2

Applications & Data Models

استخدامات الـ Databases وتاريخ الـ Data Models

Applications: enterprise information (sales, accounting, HR, manufacturing, online retail), banking & finance (banking, credit cards, trading), universities, airlines (among the first to use geographically distributed databases), and telecommunication.

A data model is a template — a collection of high-level data description constructs that hide low-level storage details. A semantic data model (e.g. the ER model) is a more abstract model that helps the designer produce a good initial description, later translated to the model the DBMS supports.

عالشرح بالعربيالترتيب الزمني اللي بيتسأل كل سنة
  • الـ data model = قالب بيوصف البيانات بشكل عالي المستوى ويخبّي تفاصيل التخزين. أغلب الـ DBMSs النهارده relational.
  • الـ semantic data model زي الـ ER model: بنستخدمه في الأول عشان نرسم الـ entities والعلاقات بينهم، وبعدين نحوّله لـ relational.
  • الترتيب الزمني — احفظه بالظبط:

  • الـ semi-structured: عناصر من نفس النوع ممكن يبقى ليها attributes مختلفة، والـ XML هو اللي بيمثلها (سؤال Mid 2026 B).

1.3

Three Levels of Data Description & Data Independence

الـ ٣ مستويات والـ Data Independence

Database schema: a description of the data in terms of the database model.

Data independence: application programs are isolated from changes in the way the data is structured and stored. It is achieved by describing data at three levels of abstraction:

LevelWhat it describesHow many
Externalcustomized (and authorized) data access for individual users / groups — the user's viewseveral
Conceptual (logical)the stored data in terms of the DBMS data model — the logical structure of the whole database · produced by conceptual database designexactly one
Physical (internal)storage details: file organizations and indexes on disks · produced by physical database designexactly one
عالشرح بالعربيمين بيوصف إيه
  • الـ data independence يعني البرامج اللي شغالة على البيانات مش بتتأثر لو غيّرنا طريقة تخزين البيانات أو تنظيمها. وده بيتحقق بإننا نوصف البيانات على ٣ مستويات.
  • External: اللي كل مستخدم (أو مجموعة) شايفه — يعني الـ user's view. ممكن يبقى في أكتر من واحد.
  • Conceptual (اسمه كمان logical): الهيكل المنطقي للـ database كلها بلغة الـ data model (يعني الـ tables والـ attributes). فيه واحد بس.
  • Physical (اسمه كمان internal): إزاي البيانات متخزنة على الـ disk فعلًا — تنظيم الملفات والـ indexes. فيه واحد بس.
  • سؤال Mid 2026 A: «الـ physical schema بيركز على؟» ← data storage and access paths. وسؤال: «الـ conceptual schema بيوصف؟» ← the logical structure of the entire database.
  • سؤال: «البيانات بتتوصف على كام مستوى؟» ← ٣.
فخ: «Conceptual schema summarizes how to store data and auxiliary data structures such as indexes» ← False — ده وصف الـ Physical.
1.4

People Who Work with DBMSs

الناس اللي بتشتغل مع الـ DBMS

  1. DBMS designers & implementers — build the DBMS software.
  2. End users — wish to store and use data in a DBMS, through applications written by programmers.
  3. Database application programmers (database developers) — develop packages that facilitate data access for end users, using host/data languages and vendor tools.
  4. Database Administrator (DBA) — responsible for:
    • Designing the conceptual and physical schemas.
    • Security & authorization — no unauthorized access.
    • Database tuning — modifies the schemas as needs evolve.
    • Data availability & recovery from failure — periodic backups, logs, restore to a consistent state.
عالشرح بالعربيمين بيعمل إيه — أكتر حتة بتلخبط
  • DBMS implementers: هما اللي بيبنوا برنامج الـ DBMS نفسه (زي اللي عملوا Oracle). سؤال «Database implementor is responsible for…» ← building / developing the DBMS software.
  • End users: اللي عايزين يخزنوا البيانات ويستخدموها — بيستخدموا البرامج الجاهزة.
  • Application programmers: بيعملوا البرامج (packages) اللي بتسهّل على الـ end users الوصول للبيانات.
  • الـ DBA عنده ٤ مهام: (١) يصمم الـ conceptual والـ physical schema، (٢) الأمان والصلاحيات، (٣) tuning يعني يعدّل الـ schemas مع تغيّر الاحتياجات، (٤) الـ availability والـ recovery — backup دوري، logs، ويرجّع البيانات لحالة سليمة بعد أي عطل.
فخاخ مشهورة: «Database implementors develop packages for end users» ← False (دي شغلانة الـ application programmers). «Database implementor is responsible for data availability & recovery» ← False (دي شغلانة الـ DBA). «DBA is responsible for developing the DBMS» ← False (ده الـ implementer). «Design of conceptual & physical schema are duties of the DBA» ← True، و«…of application programmers» ← False.
للحفظ: implementer يبني الـ DBMS · programmer يبني البرامج · end user يستخدم · DBA يصمم ويحمي ويضبط ويرجّع.
1.5

Database Languages: DDL, DML & the Data Dictionary

لغات الـ Database والـ Data Dictionary

  • DDL (Data-Definition Language): specifies the database (conceptual) schema — creation, deletion, and modification of the conceptual schema.
  • DML (Data-Manipulation Language): expresses queries and updates. DML does not affect the schema, but may affect the content.
  • DML access types: retrieval (query), insertion, deletion, modification (update).
  • DDL and DML are parts of one language: SQL (Structured Query Language) — a high-level, declarative language.
  • The output of DDL goes to the data dictionary, which holds metadata (data about data). It is a special type of file accessed and updated only by the database system, which consults it before reading or modifying data.
عالشرح بالعربيDDL للهيكل · DML للمحتوى
  • DDL = لغة تعريف الهيكل: تعمل الـ schema وتمسحها وتعدّلها (CREATE, DROP, ALTER). سؤال: «To create, modify and delete conceptual schema we use…» ← SQL-DDL.
  • DML = لغة التعامل مع البيانات: استعلام وإضافة وحذف وتعديل. سؤال: «To express queries and updates we use…» ← SQL-DML.
  • الـ DML مابتغيّرش الـ schema، لكن ممكن تغيّر المحتوى (content). سؤال: «SQL-DML does affect the … of the database» ← content.
  • الاتنين جزء من لغة واحدة اسمها SQL، وهي لغة high-level (سؤال «SQL is one of the high-level languages» ← True).
  • ناتج الـ DDL بيتحط في الـ data dictionary: فيه metadata يعني بيانات عن البيانات (أسماء الـ tables والأنواع والـ constraints). وهو نوع خاص من الملفات (data file) مايقدرش يلمسه غير الـ database system نفسه.
سؤال متكرر: «Data dictionary is considered to be a special type of…» ← data file.
1.6

Integrity Constraints (Overview)

الـ Integrity Constraints — النظرة العامة

Integrity constraints (ICs) are conditions specified on the database schema that the stored data must satisfy. The DBMS checks them every time the database is updated. ICs are specified when the database is created and enforced when a database application is run.

  1. Domain constraints — every attribute has a domain (integer, char, date…); the most elementary IC.
  2. Referential integrity — a value appearing in one entity must also appear in another (e.g. a course's department must exist). Violations are normally rejected.
  3. Assertions — any condition the database must always satisfy (e.g. "every department offers at least five courses each semester"). Domain & referential constraints are special forms of assertions.
  4. Authorization — read, insert, update, delete authorization; a user may get all, none, or a combination.
عالشرح بالعربيبتتحدد إمتى وبتتطبق إمتى
  • الـ ICs = شروط على البيانات عشان مايدخلش بيانات غلط. مثال: رصيد القسم عمره ما يبقى سالب.
  • بتتحدد (specified) وإحنا بنعمل الـ database، وبتتطبق (enforced) وقت تشغيل التطبيق — يعني كل ما حد يعدّل البيانات.
  • الأنواع: Domain (نوع ومدى القيمة)، Referential integrity (القيمة لازم تكون موجودة في جدول تاني)، Assertions (أي شرط عام)، Authorization (صلاحيات read/insert/update/delete).
  • سؤال Final 2026: «Integrity constraints ensure…» ← accuracy, consistency, and reliability.
فخ: «Integrity constraints are enforced when creating databases» ← False. بتتحدد وقت الإنشاء، لكن بتتطبق وقت running a database application.
1.7

Structure of a DBMS

مكونات الـ DBMS من جوه

Two sources of commands: DDL commands from the DBA (schema) and query/DML commands from users and applications.

ComponentJob
DDL processorparses schema-altering commands, passes them to the execution engine
Query compilerparses & optimizes a query → query plan
Execution engineexecutes the plan; requests small pieces of data
File / index / record managerknows data files & indexes, finds data quickly
Buffer managerpartitions main memory into page-sized buffers; manages data pages in memory
Storage managermoves data between disk and buffers
Transaction managerhandles transactions; deadlock resolution (roll back / abort)
Log manager / recoverylogging every change for durability; recovery after a crash
Schedulerconcurrency control using locks (kept in a lock table)

Information in buffers: data, metadata, log data, statistics, indexes.

A transaction is a group of database operations executed as one unit, atomically and in apparent isolation. Funds-transfer example: Atomicity (all or nothing), Consistency (sum of balances preserved), Durability (results persist after failure).

عالشرح بالعربيرحلة الـ query جوه الـ DBMS
  • فيه نوعين أوامر بيدخلوا الـ DBMS: أوامر DDL من الـ DBA (بتغيّر الـ schema)، وأوامر DML من المستخدمين والبرامج.
  • رحلة الـ query: الـ query compiler بيحلّل الـ query ويحسّنها ويطلّع query plan (خطوات التنفيذ) ← الـ execution engine بينفّذ الخطة ويطلب البيانات ← الـ file/index manager يعرف البيانات فين ← الـ buffer manager يجيب الصفحات للميموري ← الـ storage manager يتعامل مع الـ disk.
  • الـ buffer manager بيقسّم الميموري لـ buffers بحجم الـ page. فالـ buffers جزء من الـ main memory.
  • الـ transaction = مجموعة عمليات لازم تتنفذ كوحدة واحدة. مثال تحويل فلوس من حساب A لحساب B: لازم السحب والإيداع يحصلوا مع بعض أو مايحصلوش خالص (Atomicity)، ومجموع الرصيدين يفضل زي ما هو (Consistency)، والنتيجة تفضل حتى لو الجهاز وقع (Durability).
  • الـ log manager بيسجّل كل تغيير عشان لو حصل crash الـ recovery manager يرجّع البيانات لحالة سليمة. والـ scheduler بيستخدم locks عشان الـ transactions ماتبوظش بعض. ولو حصل deadlock (كل واحد مستني التاني)، الـ transaction manager بيلغي (rollback) واحد منهم.
فخ متكرر جدًا: «Execution engine is the component responsible for producing the query plan» ← False — اللي بيطلّع الـ plan هو الـ Query compiler. الـ execution engine بينفّذها بس.
سؤال Mid 2026 B: التوصيلة الصح ← Buffer Manager → Manages data pages in main memory.
1.8

Database Access from Applications & Tier Architectures

الـ Client-Server والـ Tiers

Client machines: where remote database users work · Server machines: where the database system runs.

ArchitectureWhere things live
One-tierapplication program and database system reside at the server machine
Two-tierapplication at the client; it calls the database system at the server through query-language statements
Three-tierclient = front end only (forms) → application server (holds the application logic) → database server · best for large and web applications
  • SQL is declarative and not as powerful as procedural languages; input/output and networking are written in a host language (C, C++, Java) with embedded SQL.
  • Two ways to run DML from a host language: an API — ODBC (C) or JDBC (Java) — or embedding DML calls, converted by a DML pre-compiler.
عالشرح بالعربيكل حاجة قاعدة فين
  • One-tier: البرنامج والـ database الاتنين على الـ server.
  • Two-tier: البرنامج على جهاز المستخدم (client)، وبيكلّم الـ database اللي على الـ server بـ SQL.
  • Three-tier: جهاز المستخدم واجهة بس، وفي النص application server فيه منطق البرنامج، وبعده الـ database server. ده الأنسب للتطبيقات الكبيرة والـ web.
  • سؤال: «إيه اللي موجود في الـ server ومش في الـ client؟» ← Database.
  • الـ SQL لغة declarative (بتقول عايز إيه مش إزاي)، فبنحطها جوه لغة زي C أو Java. وبنوصل بـ ODBC (لـ C) أو JDBC (لـ Java).
سؤال متكرر: «In … architecture, the application program and database system reside at the server machine» ← one-tier. و«Common for Web applications» ← three-tier.

Relational Databases

The relational data model (schema, instance, degree, cardinality), external schemas and views, integrity constraints (domain, keys, foreign keys), SQL-DDL (CREATE / ALTER / DROP), SQL-DML (INSERT / DELETE / UPDATE), foreign-key actions, and deferred constraints.

الـ relational model بالتفصيل: الـ schema والـ instance والـ degree والـ cardinality، والـ views، وأنواع الـ keys، والـ foreign key، وأوامر SQL لإنشاء الجداول وتعديلها، وإيه اللي بيحصل لما نمسح صف ليه صفوف بتشاور عليه.

2.1

The Relational Data Model

الـ Relation: schema و instance و degree و cardinality

The central construct is the relation — informally a table of records (tuples) — consisting of a relation schema and a relation instance.

  • Relation schema: the relation's name + the name, type, and domain of each field (column / attribute). e.g. Students(sid: string, name: string, login: string, age: integer, gpa: real)
  • Relation instance (state): a set of tuples. No two rows are identical, and the order of tuples is irrelevant.
  • Degree = number of fields · Cardinality = number of tuples.
  • Relational database schema = collection of relation schemas · Relational database = collection of relation instances with distinct names.
  • Both entities (Students, Courses…) and relationships (Enrolled, Teaches…) are modeled as relations.
  • In an RDBMS the conceptual level = the relational database schema; the physical level decides file organizations and indexes. A DBMS file is a collection of records/pages, not a string of characters.

  • الـ relation = جدول. ليه جزئين: schema (اسم الجدول وأسماء الأعمدة وأنواعها — يعني القالب) وinstance (الصفوف الموجودة فعلًا دلوقتي).
  • الـ instance عبارة عن set of tuples — يعني مفيش صفين زي بعض بالظبط، وترتيب الصفوف مش مهم. سؤال Mid 2026 A: «An instance of a relation is…» ← set of tuples.
  • Degree = عدد الأعمدة. Cardinality = عدد الصفوف. في المثال: degree = 5 و cardinality = 6.
  • Relational database schema = مجموعة الـ schemas. Relational database = مجموعة instances. سؤال: «Relational Database is a collection of relations…» ← instances.
  • في الـ relational model، الـ entities (زي Students) والـ relationships (زي Enrolled) الاتنين بيتمثلوا كـ relations.
للحفظ: Cardinality = Count of rows (عدد الصفوف) · Degree = عدد الأعمدة.
فخ: «Degree of the relation is the number of tuples» ← False — ده الـ Cardinality.
2.2

External Schema & Views

الـ External Schema والـ View

  • A database has exactly one conceptual schema and one physical schema, but may have several external schemas, each tailored to a group of users.
  • An external schema = a collection of views and relations from the conceptual schema. Its design is guided by end-user requirements (a duty of application programmers).
  • A view is conceptually a relation, but its records are not stored in the RDBMS — they are computed from the view definition when needed. e.g. Courseinfo(cid, fname, enrollment)
  • Storing it would be redundant — wasted space and possible inconsistencies.
  • A materialized view is a view whose result is stored on disk.
عالشرح بالعربيView عادية ولا Materialized؟
  • الـ external schema بتسمح إن كل مستخدم أو مجموعة يشوفوا البيانات بالشكل اللي يناسبهم. سؤال: «External schema is designed to allow data access to be customized at the level of individual users» ← True.
  • تصميم الـ external schema شغلانة الـ application programmers (سؤال: «Design of … schema is a duty of application programmers» ← external).
  • الـ view = جدول «وهمي»: بيتحسب من الجداول الأساسية وقت ما تطلبه، ومش متخزن على الـ disk.
  • ليه مانخزنهاش؟ لأن ده هيبقى تكرار (redundancy) — مساحة ضايعة، وممكن البيانات تبقى مش متطابقة. مثلًا لو طالب سجّل في كورس ونسينا نزوّد عدد الطلبة في الـ view المتخزنة.
  • الـ materialized view هي view نتيجتها متخزنة فعلًا.
فخ متكرر: «View is composed from base relations but is not stored on disk» ← True. لكن «Materialized View … is not stored on disk» ← False.
2.3

Integrity Constraints: Domain & Keys

الـ Domain والـ Candidate / Primary / Super Keys

ICs are conditions on the schema that restrict the data that can be stored. An instance satisfying all ICs is a legal instance; the RDBMS stores only legal instances.

  • Domain constraint: values in a column must be drawn from its domain — it restricts the values a field can take.
  • Key (candidate key): a minimal set of fields that uniquely identifies a tuple: (1) no two distinct tuples have identical values in all key fields; (2) no proper subset of the key is a unique identifier.
  • Primary key: the candidate key chosen by the designer. Every relation has one; it cannot be NULL; it is dataless (values never or very rarely change — e.g. SSN, not address).
  • Superkey: any set of fields containing a key, e.g. (sid, name). Formally: K is a key if K is a superkey and no proper subset of K is a superkey.
  • NULL = the value is unknown or does not exist (not applicable).
عالشرح بالعربيالفرق بين الـ keys
  • Domain constraint: القيمة لازم تكون من النوع والمدى المسموح للعمود (مثلًا gpa رقم من 0 لـ 4). يعني بيقيّد القيم — مش عدد الأعمدة.
  • Candidate key: أقل مجموعة أعمدة تميّز كل صف عن التاني. شرطين: (١) مفيش صفين ليهم نفس القيمة فيها، (٢) لو شيلت أي عمود منها ماتبقاش مميِّزة (يعني minimal).
  • Primary key: واحد من الـ candidate keys بنختاره. لازم يبقى موجود في كل relation، ومينفعش يبقى NULL، وdataless يعني قيمته مابتتغيرش تقريبًا (الرقم القومي آه، العنوان لأ).
  • Superkey: أي مجموعة أعمدة فيها key — حتى لو فيها أعمدة زيادة. مثلًا (sid, name) superkey لأنها فيها sid. فالـ superkey ممكن تحتوي key و foreign key مع بعض.
  • التعريف الرسمي: K يبقى key لو هو superkey ومفيش جزء أصغر منه superkey.
  • NULL معناها: القيمة مش معروفة أو مش منطبقة (unknown or not applicable).
every key is a superkey · a superkey is a key only if it is minimal
فخاخ: «Candidate keys are responsible for differentiating between records» ← True. «Foreign keys … differentiating between records» ← False. «Null is not possible for primary key» ← True. «Domain constraint restricts the number of fields» ← False.
2.4

Referential Integrity (Foreign Keys)

الـ Foreign Key والـ Referencing / Referenced

A tuple can be referred to from elsewhere by storing the values of its primary key. In Enrolled(studid, cid, grade), every studid must appear as a sid in Students → studid is a foreign key referring to Students.

  • The relation containing the foreign key (Enrolled) is the referencing relation; the one it points to (Students) is the referenced relation.
  • The foreign key must match the primary key of the referenced relation: same number of columns and compatible types (names may differ).
  • Some referenced tuples may be unreferenced (e.g. sid 50000), but every FK value must exist in the referenced PK column.
  • A foreign key can refer to the same relation — so a relation can be both referencing and referenced.
  • Foreign keys may be NULL (unless they are part of the primary key).
عالشرح بالعربيمين بيشاور على مين
  • الـ foreign key = عمود في جدول بيشاور على الـ primary key في جدول تاني. مثال: studid في Enrolled بيشاور على sid في Students — عشان مايسجّلش طالب مش موجود.
  • الجدول اللي فيه الـ foreign key اسمه referencing (اللي بيشاور)، والجدول اللي بيتشاور عليه اسمه referenced.
  • الـ foreign key لازم يطابق الـ primary key: نفس عدد الأعمدة وأنواع متوافقة — الأسماء عادي تختلف.
  • ممكن يبقى في طلبة مش مسجلين في أي كورس (زي 50000) — ده عادي. المهم إن أي studid في Enrolled يكون موجود في Students.
  • الـ foreign key ممكن يشاور على نفس الجدول (زي super_ssn في EMPLOYEE بيشاور على ssn) — فالجدول ممكن يبقى referencing و referenced في نفس الوقت.
  • الـ foreign key ينفع يبقى NULL (إلا لو كان جزء من الـ primary key).
فخاخ: «The relation which contains a foreign key is called referenced» ← False (اسمها referencing). «Null is not possible for foreign key» ← False. «A relation R cannot play as referencing and referenced at the same time» ← False.
2.5

SQL-DDL: CREATE, ALTER, DROP & Keys

إنشاء الجداول وتعديلها في SQL

SQL-DDL specifies: the schema of each relation, the types of values, the integrity constraints, the indices, the security & authorization information, and the physical storage structure.

CREATE TABLE Students (
  sid    CHAR(20),
  name   CHAR(30),
  login  CHAR(20) NOT NULL DEFAULT 0000,
  age    INT,
  gpa    REAL NOT NULL CHECK (gpa >= 0 AND gpa <= 4),
  UNIQUE (name, age),
  CONSTRAINT StudentsKey PRIMARY KEY (sid) )

CREATE TABLE Enrolled (
  studid CHAR(20), cid CHAR(20), grade CHAR(10),
  PRIMARY KEY (studid, cid),
  FOREIGN KEY (studid) REFERENCES Students )
عالشرح بالعربيمعنى كل سطر — سؤال مقالي ثابت
  • CREATE TABLE بتعمل جدول جديد وتحدد اسمه وأعمدته وأنواعها.
  • login CHAR(20) NOT NULL DEFAULT 0000: الـ login نص طوله 20، لازم يبقى ليه قيمة، ولو ماحطيتش قيمة بياخد 0000 تلقائي.
  • gpa REAL NOT NULL CHECK (gpa >= 0 AND gpa <= 4): رقم عشري، لازم يبقى موجود، وبين 0 و 4. والـ CHECK هو اللي بيعمل الـ domain constraint.
  • UNIQUE (name, age): مفيش طالبين ليهم نفس الاسم ونفس السن مع بعض — يعني (name, age) candidate key. والـ UNIQUE هو اللي بيعمل الـ key constraint.
  • CONSTRAINT StudentsKey PRIMARY KEY (sid): الـ sid هو الـ primary key، واسم الـ constraint ده StudentsKey — لو حصل خطأ الاسم ده بيظهر عشان تعرف المشكلة فين.
  • FOREIGN KEY (studid) REFERENCES Students: أي studid لازم يكون موجود كـ sid في Students.
  • في Enrolled، الـ primary key هو (studid, cid) — يعني الطالب ليه درجة واحدة بس في كل كورس.
  • DROP TABLE R بيمسح الجدول وتعريفه كمان. وALTER TABLE … ADD يضيف عمود، وALTER TABLE … DROP يشيل عمود من الـ schema ومن كل الصفوف.
للحفظ: CHECK ← domain · UNIQUE ← key · DROP TABLE ← يمسح الجدول وتعريفه · ALTER TABLE … DROP col ← يشيل العمود من كل الصفوف.
2.6

SQL-DML: INSERT, DELETE, UPDATE & Violations

تعديل البيانات وإيه اللي بيكسر الـ constraints

INSERT INTO Students (sid, name, login, age, gpa)
VALUES (53688, 'Smith', 'smith@ee', 18, 3.2)

DELETE FROM Students S WHERE S.name = 'Smith'

UPDATE Students S
SET S.age = S.age + 1, S.gpa = S.gpa - 1
WHERE S.sid = 53688
  • In UPDATE, WHERE is applied first (which rows), then SET (how). On the right side of =, the old value is used.
  • ICs are specified when a relation is created and enforced when an instance is modified. Domain, PRIMARY KEY, and UNIQUE violations by INSERT / DELETE / UPDATE are rejected.
  • Violations are checked at the end of each SQL statement (can be deferred to the end of the transaction).
  • SQL has one basic statement for retrieval: SELECT.

Book exercise (Students instance in Fig. 2.1):

StatementViolation
INSERT … VALUES (53688, 'Mike', …)primary key — sid 53688 already exists
INSERT … VALUES (null, 'Mike', …)primary key cannot be NULL
UPDATE … SET S.sid = 50000 WHERE S.sid = 53688primary key — sid 50000 already exists
INSERT INTO Enrolled … ('Hindi101', 'B', 51111)foreign key — no student 51111
عالشرح بالعربيWHERE الأول وبعدين SET
  • INSERT بيضيف صف، وDELETE بيمسح صفوف، وUPDATE بيعدّل قيم أعمدة في صفوف موجودة. سؤال: «UPDATE is used for changing the…» ← attribute values in a table (مش الـ schema).
  • في الـ UPDATE: الـ WHERE بيتنفذ الأول (يحدد الصفوف)، وبعدين الـ SET (يحدد هيتغيروا إزاي). ولو العمود موجود في الناحيتين، الناحية اليمين بتستخدم القيمة القديمة.
  • مثال الكتاب: SET S.gpa = S.gpa - 0.1 WHERE S.gpa >= 3.3 ← بيأثر على Dave (3.3 ← 3.2) و Jones (3.4 ← 3.3) و Smith اللي الـ gpa بتاعه 3.8 (← 3.7). Jones دلوقتي بقى 3.3 بس ده مش هيخليه يتعدّل تاني — الـ WHERE اتحسب مرة واحدة.
  • الـ ICs بتتحدد وقت إنشاء الجدول وبتتطبق وقت تعديل البيانات. لو أي INSERT أو UPDATE كسر domain أو primary key أو unique ← بيترفض.
  • الكسر بيتشيك عليه في آخر كل statement (إلا لو الـ constraint كانت deferred).
سؤال «أكمل»: «SQL has one basic statement for retrieving information; the … statement» ← SELECT.
2.7

Foreign-Key Actions & Deferred Constraints

CASCADE و NO ACTION و SET NULL و DEFERRED

For Enrolled.studid → Students.sid:

  1. Insert an Enrolled row with a non-existent studid → simply rejected.
  2. Delete a Students row → options: delete the referring Enrolled rows (CASCADE) · disallow the deletion (NO ACTION) · set studid to a default student (SET DEFAULT) · set studid to NULL (SET NULL — impossible here because studid is part of Enrolled's PK).
  3. Update a Students primary key → the same options.
FOREIGN KEY (studid) REFERENCES Students
   ON DELETE CASCADE
   ON UPDATE NO ACTION
OptionEffect
NO ACTION (default)the delete / update is rejected
CASCADEdelete → referring rows deleted too · update → the change is carried into referring rows
SET DEFAULTreferring rows switch to a default value (e.g. studid CHAR(20) DEFAULT '53666')
SET NULLreferring rows get NULL

Deferred constraints: by default a constraint is checked at the end of every SQL statement (IMMEDIATE). SET CONSTRAINT ConstraintFoo DEFERRED → checked at commit time. Needed for circular FKs (Students.honors → Courses, Courses.grader → Students): insert one, insert the other, then commit.

عالشرح بالعربيلو مسحت الطالب، تسجيلاته يحصلها إيه؟
  • لو ضفت تسجيل لطالب مش موجود ← الـ INSERT بيترفض على طول.
  • لو مسحت طالب ليه تسجيلات، عندك ٤ اختيارات:
CASCADE → delete his enrollments too · NO ACTION → reject the delete · SET DEFAULT → move them to a default student · SET NULL → put NULL
  • الـ default لو ماكتبتش حاجة هو NO ACTION (يعني يترفض).
  • سؤال Mid 2026 A: «لما صف في الـ referenced يتمسح عايزين الصفوف المرتبطة بيه تتمسح تلقائي» ← ON DELETE CASCADE.
  • سؤال Mid 2026 B: DELETE FROM Students WHERE sid = 50000 مع ON DELETE CASCADE ← الطالب وكل تسجيلاته بيتمسحوا.
  • الـ SET NULL مينفعش في مثال Enrolled لأن studid جزء من الـ primary key، والـ primary key مايبقاش NULL.
  • DEFERRED: عادة الـ constraint بيتشيك عليه بعد كل statement (IMMEDIATE). لو خليته DEFERRED بيتشيك عليه وقت الـ commit (آخر الـ transaction). ده مهم لما يبقى في جدولين كل واحد بيشاور على التاني — مش هتعرف تضيف أول صف غير لو أجّلت الفحص.
للحفظ: DEFERRED ← at commit time · DEFERRABLE INITIALLY DEFERRED ← checked at the end of the transaction.

Design the Schema

The essay half of the midterm: turning a story into relations with primary and foreign keys, drawing an ERD, mapping it to tables, and writing CREATE TABLE statements.

نص درجة الميد-term مقالي: قصة تحوّلها لجداول بالـ primary والـ foreign keys، أو ERD ترسمه، أو أوامر CREATE TABLE تكتبها. هنا الطريقة خطوة بخطوة.

3.1

From a Story to a DB Schema

إزاي تحوّل القصة لجداول

  1. Nouns → entities → tables. Each table gets its own id as the primary key.
  2. Descriptions → attributes. "has Id, name and phone" → columns.
  3. 1 : N ("a customer places many orders; an order is placed by one customer") → put the PK of the "one" side as an FK in the "many" side.
  4. M : N ("an order lists many items; an item may be on many orders") → a new relationship table whose PK is the pair of FKs; relationship attributes (quantity, date, fine…) go here.
  5. Recursive ("a salesperson manages other salespeople") → an FK in the same table pointing to its own PK (e.g. manager_id).
  6. 1 : 1 → FK on either side (usually the side with total participation), declared UNIQUE.
Notation: underline (or write PK) the primary key · mark each FK → Table(column)
عالشرح بالعربي٥ قواعد بتحل أي سؤال schema
  • الأسماء في القصة (طالب، كتاب، عميل، أوردر) ← كل واحد جدول، وليه id يبقى الـ primary key.
  • الصفات (له اسم وعنوان وتليفون) ← أعمدة في الجدول.
  • علاقة واحد لكتير (1:N): خد الـ PK بتاع ناحية «الواحد» وحطه FK في ناحية «الكتير». مثال: العميل بيعمل أوردرات كتير ← customer_id يتحط في جدول Order.
  • علاقة كتير لكتير (M:N): لازم جدول جديد في النص، والـ PK بتاعه هو الـ FKs الاتنين مع بعض. وأي صفة خاصة بالعلاقة نفسها (الكمية، تاريخ الاستعارة، الغرامة) بتتحط في الجدول ده.
  • علاقة الجدول بنفسه (recursive): زي «البياع بيدير بياعين تانيين» ← عمود manager_id في نفس الجدول بيشاور على salesperson_id.
غلطة بتضيّع درجات: إنك تحط FK لعلاقة M:N في واحد من الجدولين بدل ما تعمل جدول وسيط. M:N دايمًا = جدول جديد.
في الورقة: اكتب كل جدول على سطر، وحط خط تحت الـ PK أو اكتب جنبه PK، وجنب كل FK اكتب بيشاور على أنهي جدول.

  • Noun → table with id as PK · description → columns
  • 1:N → FK on the N side
  • M:N → new table, PK = both FKs (+ relationship attributes)
  • Recursive → FK to the same table (manager_id)
  • ERD: rectangle entity · oval attribute · diamond relationship · double rectangle weak entity
