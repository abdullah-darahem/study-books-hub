Software is not just code

1.1

What Is Software & Attributes of Good Software

الـ software = برامج + documentation، والـ ٤ صفات

Software = computer programs and associated documentation. Not just the programs, but also all documentation needed to set them up, operate them correctly, explain how to use the system, and websites to download recent product information.

Software engineering supports professional software development, rather than individual programming. Professional software is used by someone apart from its developer, is usually developed by teams, and is maintained and changed throughout its life.

Four important attributes that professional software must have (M-D-E-A):

AttributeMeaning
Maintainabilitymeets changing needs; future upgrades made easily, quickly, cheaply
Dependabilitytrustworthy; shouldn't cause physical or economic damage in case of failure
Efficiencyno wasteful use of system resources; memory & processor usage minimized
Acceptabilityaccepted by its users: understandable, usable and compatible with other systems
عالشرح بالعربيالبرنامج من غير documentation = نص software
  • الـ software = البرامج + الـ documentation. يعني لو عملت أبلكيشن من غير دليل استخدام ولا شرح تسطيب، إنت سلّمت نص الشغل بس. سؤال الكويز: «What is software composed of?» ← Programs and associated documentation.
  • الـ software engineering معمول للشغل الاحترافي: برنامج هيستخدمه حد غيرك، وبيعمله فريق، وبيتعدّل طول عمره.
  • الصفات الأربعة:
    • Maintainability = سهل تعدّله وتطوّره بسرعة ورخيص.
    • Dependability = تقدر تعتمد عليه، ولو وقع مايعملش كارثة.
    • Efficiency = مابياكلش الرام والبروسيسور.
    • Acceptability = اليوزر يفهمه ويستخدمه بسهولة.
  • سؤال Mid 2026 A: «users can understand and use the system easily» ← Acceptability، مش Maintainability!

1.2

SE vs CS vs System Engineering · Generic vs Customized

مين بيعمل إيه، ونوعين الـ software products

Software engineering is an engineering discipline concerned with all aspects of software production using systematic, well-defined scientific techniques. Its result: an effective and reliable software product. Engineers use a systematic approach with tools based on the problem, constraints and resources.

Software DeveloperSoftware Engineer
builds software that runs on various computersapplies SE principles to design, develop, maintain and test
primarily a solitary activityteam activity
writes a complete programworks with other components of the system (hardware + software)
uses readymade toolscreates the tools to develop software
limited scalemuch larger scale
  • System engineering: all aspects of computer-based systems: hardware, software, human work and procedures. Software engineering is part of it.
  • Computer science: theory and fundamentals (languages, graphics, AI…). Software engineering: the practicalities of developing and delivering useful software. CS gives SE its scientific foundation, as physics does for electrical engineering.

عالشرح بالعربيجاهز من المحل ولا تفصيل عند الترزي؟
  • Software Engineering = تطبيق طرق منظمة ومنهجية على تطوير السوفتوير (Mid 2026 B). الهدف: برنامج reliable and effective، مش «سريع» ولا «رخيص» ولا «معقد».
  • Developer vs Engineer: الـ developer بيشتغل لوحده وبيستخدم أدوات جاهزة. الـ engineer شغل فريق وبيعمل الأدوات نفسها.
  • CS vs SE: الـ CS نظري (خوارزميات، AI، لغات). الـ SE عملي: إزاي تطلّع منتج يشتغل ويتسلّم. سؤال Re-mid 2026 ← Practical software development.
  • System engineering أكبر: هاردوير + سوفتوير + شغل البشر. والـ SE جزء منه. (الكويز: True)
  • Generic = قميص جاهز من المحل 👕: معمول للسوق كله (Word, Photoshop). Customized = بدلة تفصيل عند الترزي 🤵: لعميل واحد (نظام تسجيل جامعة، air traffic control).
  • حيلة: لو فيه اسم جهة محددة («for a university»، «for one client») ← customized. لو «sells the same version to many businesses» ← generic.

1.3

Software Process, Key Challenges & Costs

الـ ٤ activities، والـ ٣ تحديات، والتكلفة

A software process is a sequence of activities that leads to the production of a software product. Different systems need different processes. Four fundamental activities common to all processes:

1 · Specificationcustomers & engineers define the software and its constraints (what it should do)
2 · Developmentdesign & implementation: the software is designed and programmed
3 · Validationevaluated to confirm it meets the customer's requirements (testing)
4 · Evolutionupdated to reflect changing demands (maintenance)

Key challenges facing software engineering (H-D-T):

  1. Heterogeneity: coping with increasing diversity of software & hardware platforms and fast-changing technology.
  2. Delivery: demands for reduced delivery times; techniques for faster delivery.
  3. Trust: developing trustworthy software; showing users it can be trusted.

Costs: roughly 60% development, 40% testing. For custom software, evolution costs often exceed development costs. Costs depend on the type of system, its required attributes, and the development model.

There are no universal SE methods suitable for all systems. The key factor in choosing methods is the type of application being developed.

عالشرح بالعربي٤ خطوات في أي مشروع
  • أي software process لازم يعدّي على ٤ حاجات، احفظهم بالترتيب: Specification ← Design & Implementation ← Validation ← Evolution. السؤال ده جه في Re-mid 2026 وفي الكويزات كتير.
  • تخيّلها بناء بيت: Specification = تتفق مع صاحب البيت عايز إيه · Development = ترسم وتبني · Validation = تتأكد إنه زي ما اتفقتوا · Evolution = تعلّي دور بعدين 🏠.
  • التحديات ٣ «H-D-T»: Heterogeneity (أجهزة وأنظمة كتير مختلفة) · Delivery (العميل عايزه امبارح) · Trust (الناس تثق فيه).
  • التكلفة: ٦٠٪ تطوير و٤٠٪ اختبار. وفي الـ custom، التطوير بعد التسليم (evolution) بيكلّف أكتر من التطوير نفسه.
  • مفيش طريقة واحدة تنفع لكل حاجة: نوع الـ application هو اللي بيحدد.
⏰
Delivery challenge: العميل: «محتاجه إمتى؟» · العميل نفسه: «امبارح»الـ developer وهو بيعمل git push الساعة ٣ الفجر 🥲
فخ: «Planning, Analysis, Design, Coding» و «Analysis, Coding, Deployment, Maintenance» شكلهم حلو، بس الإجابة الرسمية هي Specification, Design & Implementation, Validation, Evolution.

Issues of professional responsibility (C-C-I-C):

ResponsibilityMeaning

Waterfall, Increments & Agile

Plan-driven vs agile, the three process models (waterfall, incremental, reuse-oriented) with their advantages and disadvantages, coping with change (prototyping, incremental delivery), and agile methods: principles, XP, user stories, refactoring, pair programming and Scrum.

إمتى تستخدم Waterfall؟ ومميزات الـ Incremental (سؤال مقالي جه ٣ مرات!). وإزاي تتعامل مع التغيير، وبعدين Agile و XP و Scrum.

2.1

Process Activities & Plan-Driven vs Agile

كل حاجة متخططة من الأول، ولا خطوة خطوة؟

All processes include: software specification (functionality and constraints defined) · design & implementation · validation (testing) (does what the customer wants) · evolution (maintenance) (meets changing needs).

Process descriptions may also include: the order of activities · products (outcomes of an activity, e.g. an architecture model) · roles (project manager, configuration manager, programmer) · pre- and post-conditions (true before and after an activity).

Plan-drivenAgile
all activities planned in advance; progress measured against the planplanning is incremental; easier to change to reflect changing customer requirements
safety-critical systems (aircraft control), stable requirementsstartups continuously updating a web app, unclear/changing requirements

Each approach suits different software; you usually need a balance. There are no right or wrong software processes.

عالشرح بالعربيخطة صارمة ولا مرونة؟
  • Plan-driven = كل حاجة متخططة من الأول وبنقيس التقدم على الخطة. زي رحلة طيران: مفيش ارتجال ✈️.
  • Agile = بنخطط حتة حتة وبنتأقلم مع التغيير. زي خروجة مع صحابك: «يلا نروح هنا… لا بلاش، هناك» 😂.
  • أسئلة الكويز: «safety-critical, aircraft control, strict design» ← Plan-driven. «startup continuously updates to meet changing needs» ← Agile. «requirements unclear at the start» ← Agile (Mid 2026 B).
  • مفيش process صح وprocess غلط: كل واحدة ليها ظروفها.

The Waterfall Model

مراحل ورا بعض زي الشلال، وإمتى تستخدمه

The waterfall model is plan-driven with separate and distinct phases of specification and development. Each phase must finish before the next starts.

Requirements definitionSystem & software designImplementation & unit testingIntegration & system testingOperation & maintenance
AdvantagesDisadvantages
simple and easy to understand and implementcosts of producing and approving documents
easy to manage: each phase's documents make the process visible, so managers monitor progress against the planno working software until late stages
phases are clearly defined and completed one at a timetakes a lot of time to produce the final product
no chance to change customer requirements (contract)
high amount of risk

Mostly used for large systems engineering projects developed at several sites (the plan-driven nature helps coordinate work). Use waterfall only when:

  1. The requirements are very well understood from the beginning.
  2. The requirements are unlikely to change (stable) during development.
  3. The delivery time is not a problem.
عالشرح بالعربيالمية مابترجعش لفوق 🌊
  • اسمه Waterfall لأن كل مرحلة بتنزل على اللي بعدها ومفيش رجوع، زي الشلال.
  • الترتيب: Analysis ← Design ← Coding ← Testing ← Operation & maintenance. الـ Testing قبل الـ Operation (Mid 2025 B).
  • أكبر عيب: مفيش برنامج شغال غير في الآخر خالص، والعميل مايقدرش يغيّر رأيه.
  • إمتى أستخدمه؟ ٣ أسباب، سؤال مقالي جه ٣ مرات (Mid 2025 B، Mid 2026 A): المتطلبات واضحة جدًا + مش هتتغير + الوقت مش مشكلة.
🌊
العميل بعد ٨ شهور Waterfall: «ده مش اللي أنا كنت عايزه»الفريق: «حضرتك مضيت على الـ requirements من ٨ شهور» 📄🙂
فخ: «Waterfall allows frequent changes to requirements» ← False. ولو سألك «best described as» ← plan-driven with distinct phases، مش «iterative».
2.3

Incremental Development

نسخة ورا نسخة، والمميزات الـ ٣ (مقالي متكرر!)

The system is developed as a series of versions (increments), each adding functionality to the previous one. Develop an initial implementation, expose it to user comment, evolve it through several versions. Specification, development and validation are interleaved. May be plan-driven or agile (mostly agile).

Three benefits compared to waterfall ESSAY 3×

  1. The cost of accommodating changing customer requirements is reduced: much less analysis and documentation to redo.
  2. More rapid delivery and deployment of useful software to the customer, even without all functionality.
  3. It is easier to get customer feedback on the work done; only the current increment has to change.

Two problems

  1. The process is not visible: managers need regular deliverables; documenting every version isn't cost-effective.
  2. System structure tends to degrade as new increments are added, unless time and money are spent on refactoring.
عالشرح بالعربيزي ما بتبني لعبة Lego حتة حتة 🧱
  • بدل ما تسلّم كل حاجة مرة واحدة، بتسلّم نسخة صغيرة وتزوّد عليها. زي واتساب: الأول رسايل بس، وبعدين صور، وبعدين كول، وبعدين ستوري.
  • المميزات ٣ (احفظهم بالنص، جم في Mid 2024 A و Re-mid 2026 وكويزات):
    ١. تكلفة التغيير أقل.
    ٢. تسليم أسرع لحاجة مفيدة.
    ٣. feedback من العميل أسهل.
  • العيوب ٢: مش visible (المدير مش عارف وصلنا لفين) · الـ structure بيبوظ مع كل إضافة لو ماعملتش refactoring.
  • سؤال Mid 2024 A: «main advantage of incremental» ← High flexibility for changes. وكويز: «drawback» ← system structure degradation over time.

2.4

Reuse-Oriented Software Engineering

ماتخترعش العجلة من الأول

Based on a significant number of reusable components. Development focuses on integrating these components into a system rather than developing them from scratch. Components are called COTS (commercial off-the-shelf systems). May be plan-driven or agile.

Three types of reusable components: (1) stand-alone application systems (COTS) configured for a particular environment · (2) collections of objects developed as a package to be integrated with a component framework such as .NET or J2EE · (3) web services available for remote invocation.

AdvantagesDisadvantages
reduces the amount of software to develop → less cost and riskloss of control over evolution of reused elements
faster deliveryrequirements compromises are inevitable → system may not meet real user needs
عالشرح بالعربياشتري جاهز وركّب
  • بدل ما تعمل كل حاجة من الصفر، بتجمّع components جاهزة (COTS). زي بناء PC: بتشتري كارت شاشة ورامات جاهزين وتركّبهم 🖥️.
  • سؤال Re-mid 2025: «integrating existing components rather than from scratch» ← reuse-oriented model.
  • العيب المشهور: requirements compromises: الحاجة الجاهزة مش معمولة ليك بالظبط، فلازم تتنازل عن شوية متطلبات. (Mid 2026 A)
  • والعيب التاني: مالكش تحكّم في تطوير الحتة الجاهزة (لو الشركة وقفتها، إنت اتعلّقت).
🛒

2.5

Coping with Change: Prototyping & Incremental Delivery

Change avoidance و change tolerance، والـ prototype

Change is inevitable (business changes, new technologies, changing platforms). Change leads to rework, so costs include rework plus implementing new functionality. Two approaches to reduce rework costs:

Change avoidanceChange tolerance
the process includes activities that predict possible changes before significant rework; e.g. a prototype shown to customersthe process is designed so changes can be accommodated at relatively low cost; usually some form of incremental development

Two ways of coping with changing requirements: system prototyping (supports change avoidance) and incremental delivery (supports both avoidance and tolerance).

A prototype is an initial version of a system used to demonstrate concepts, try out design options and find out more about the problem. Used in requirements engineering (gathering and validation, new ideas) and in design (explore options, UI design). Prototypes focus on areas not well understood, may leave out error checking, and focus on functional rather than non-functional requirements.

Throw-away prototypes should be discarded: can't meet non-functional requirements · normally undocumented · structure degraded by rapid change · won't meet quality standards.

Incremental delivery: increments are deployed for end-users; highest-priority requirements come first. Advantages: customers get value early · early increments act as prototypes · most important services get the most testing · lower risk of overall project failure. Problems: hard to identify common facilities needed by all increments · no complete specification until the last increment conflicts with contracts.

Incremental development vs delivery: development = evaluate each increment with customers without deploying it (normal in agile); delivery = deploy increments for real use.

عالشرح بالعربياتوقّع التغيير، أو اتعايش معاه
  • Change avoidance = توقّع التغيير قبل ما يحصل: تعمل prototype وتوريه للعميل بدري.
  • Change tolerance = التغيير يحصل بس بتكلفة قليلة (Mid 2026 A: «accepting changes easily and cheaply»).
  • Prototype = بروفة سريعة للسيستم عشان العميل يشوف ويقول رأيه. الـ Prototype model = quick creation of a model to visualize requirements (جه ٣ مرات!). وبيُستخدم عشان refine & establish requirements gathering (Re-mid 2025).
  • Throw-away = بعد ما تخلص منه ارميه، ماتبنيش عليه: مش موثّق ومهلهل.
  • Incremental delivery: بتسلّم أهم حاجة الأول ← العميل يستفيد بدري + مخاطرة أقل.
🎭
الـ Prototype: «أنا مجرد بروفة، ماتبنوش عليّا!»المانجر: «ده شغال، يلا نطلّعه production» 💀
فخ: «Coping with change involves» ← change avoidance and change tolerance، مش «document freezing» ولا «ignoring changes».
2.6

Agile: Principles, XP, Refactoring & Pair Programming

الـ Agile Manifesto والـ Extreme Programming

Why agile? Customers often don't know exactly what they want; not all requirements can be identified at the beginning; requirements and priorities change; changes cause costly rework in plan-driven methods; rapid delivery is a basic requirement. Agile wasn't created because plan-driven is "bad", but because software development itself is unpredictable.

Agile principles (C-I-P-E-M): Customer involvement (closely involved throughout) · Incremental delivery (based on customer priorities) · People, not process (team uses its skills, chooses how to work) · Embrace change (design to accommodate change) · Maintain simplicity.

Extreme Programming (XP): best known agile method (late 1990s), an "extreme" approach to iterative development: new versions built several times per day · increments delivered every 2 weeks · all tests run for every build; a build is accepted only if tests pass.

User stories: an individual feature the client wants. Format: As a [user] · I want [action] · So that [benefit]. Written on cards; the team breaks them into tasks (basis of schedule and cost estimates); the customer chooses stories for the next release.

Refactoring: improving the internal structure of existing code without changing its external behaviour. Fixes the structure degradation of incremental development. Examples: reorganize a class hierarchy to remove duplicate code · clean up and rename attributes and methods · replace code with library calls. Improves understandability → less need for documentation.

Pair programming: two people working together at a single computer: same functionality as two separately, but much higher quality. Benefits: common ownership of code · informal review (each line seen by 2 people) · idea sharing · pairs are dynamic · encourages refactoring.

عالشرح بالعربياتغيّر مع التغيير 🦎
  • Agile اتعمل لأن العميل نفسه مش عارف هو عايز إيه 😂، والمتطلبات بتتغير.
  • المبادئ الـ ٥: العميل معانا · تسليم على مراحل · الناس أهم من الإجراءات · رحّب بالتغيير · خليها بسيطة.
  • XP: نسخ جديدة كذا مرة في اليوم، وتسليم كل أسبوعين، وكل التستات لازم تعدّي وإلا النسخة مرفوضة.
  • User story: «بصفتي طالب، عايز أشوف درجاتي، عشان أعرف هعيد ولا لأ» 😅.
  • Refactoring = تنضّف الكود من جوّه من غير ما تغيّر هو بيعمل إيه. زي ما تروّق دولابك: الهدوم هي هي، بس بقت مترتبة.
  • Pair programming = اتنين على جهاز واحد: واحد بيكتب والتاني بيراجع.
👯

2.7

Scrum & the Sprint Cycle

Sprint و Backlog و Scrum Master

Scrum is a general agile method that focuses on managing iterative development rather than specific practices. It doesn't prescribe pair programming or test-first, so it can be combined with XP as a management framework.

Three phases: (1) outline planning: general objectives and architecture design · (2) a series of sprint cycles, each develops an increment · (3) project closure: wraps up, completes documentation (user manuals), assesses lessons learned.

Lengthsprints are fixed: 2–4 weeks
Backlogstart point: product backlog = list of work to be done
Assesspriorities & risks reviewed; customer can add new requirements
Select & developteam + customer select features; team isolated, communication through the Scrum master
Reviewwork presented to stakeholders; next sprint begins

Scrum master: a facilitator (not a "project manager", the term is intentionally avoided because the whole team is empowered). Arranges daily meetings · tracks the backlog · records decisions · measures progress · communicates with customers and management · protects the team from external distractions.

عالشرح بالعربيسبرنت = جولة شغل من ٢ لـ ٤ أسابيع
  • Scrum = طريقة لإدارة الشغل المتكرر، مش طريقة برمجة. ممكن تستخدمه مع XP.
  • الـ Sprint = جولة شغل ثابتة ٢–٤ أسابيع. بتبدأ من الـ backlog (لستة الشغل المطلوب)، تختار حاجات، تشتغل، وتعرض على العميل.
  • Scrum Master مش مدير! ده facilitator: بينظّم الاجتماع اليومي، ويتابع الـ backlog، وبيحمي الفريق من الإزعاج. زي البودي جارد بتاع الفريق 🕴️.
🕴️
المدير: «عايز أكلّم المبرمجين ضروري»الـ Scrum Master: «هم في sprint دلوقتي، قولّي أنا وأنا أوصّل» 🛡️
فخ: Scrum مابيفرضش pair programming ولا test-first، دي حاجات XP.

3.1

Requirements, Stakeholders & User vs System Requirements

يعني إيه requirement، ومين الـ stakeholders

A requirement is a function, constraint, or other property that the system must provide to fill the needs of its users. Requirements engineering = defining, managing and testing requirements systematically: the process of establishing the services a customer requires and the constraints under which the system operates and is developed.

Functional requirements should be: Complete = all services required by the user are defined · Consistent = no contradictory definitions. For large systems, achieving both is practically impossible (easy to make mistakes; many stakeholders).

Stakeholders = any person or organization affected by the system: system owners (paying) · end users · system managers · project groups (engineers, testers, trainers) · external stakeholders (marketing, government). MHC-PMS: patients, doctors, nurses, medical receptionists, IT staff, medical ethics manager.

User requirementsSystem requirements
statements in natural language + diagrams of the services and constraintsa structured document with detailed descriptions of functions, services and operational constraints
focus on what the system should dofocus on how it will do it; defines what should be implemented
≈ BRS: "what" from a business perspective≈ SRS: "how" technically
عالشرح بالعربيكل اللي ليه علاقة بالسيستم = stakeholder
  • Complete = كل الخدمات المطلوبة متعرّفة. Consistent = مفيش تناقض (مش «مفيش تكرار»!).
  • Stakeholder = أي حد بيتأثر بالسيستم، مش العميل بس ولا المبرمجين بس. حتى الحكومة 🏛️.
  • User requirements = كلام بسيط للعميل («السيستم يطبع فاتورة»). System requirements = تفاصيل كل input وoutput وprocess للمبرمج. سؤال الكويز: «developer needs detailed descriptions of every input, output» ← System requirements.
  • Re-mid 2025: «functional requirements that provide a more detailed description» ← System requirements.

Functional vs Non-Functional Requirements

الـ classifying: بيعمل إيه ولا بيعمله إزاي؟

Functional (FR)Non-Functional (NFR)
something the system must do (what)describes how the system works: properties & constraints
phrased with noun + verbstructured with an adverb / quality word
"The system prints an invoice.""The system prints invoices quickly."
also called behavioural / operational: specify inputs, outputs and the relationships between them; how to react to inputs; may state what the system should not doproperties (reliability, safety) and constraints (response time, process, standards); often apply to the whole system; may be more critical than FRs: if not met, the system may be useless

Non-functional classifications (P-O-E):

TypeComes fromExam examples
Product (quality attributes)the delivered product must behave in a certain way: speed, reliability, usability, efficiency, security, availability"Response time shall not exceed 2 seconds" · "available 24/7" · "max 3 failures per year"
Organizationalthe customer's and developer's internal policies and procedures: process standards, implementation, environment, operational"must integrate with the existing accounting software used by the company" · "users authenticate with their staff ID card" · "developed in Java"
Externaloutside the system: government laws, regulations, industry standards, ethics"must follow government privacy regulations" · "comply with data-protection law"

Metrics for NFRs (so they can be tested): speed (transactions/sec, response time) · size (MB) · ease of use (training time) · reliability (mean time to failure, availability) · robustness (time to restart after failure) · portability (number of target systems).

Imprecision: ambiguous requirements get interpreted differently. "A user shall be able to search the appointment lists for all clinics": the user means across all clinics; the developer may implement search within one chosen clinic.

⚡ THE 3-SECOND CLASSIFIER
Q1 Is it an action the system performs (verb: generate, print, search, reset, register, provide)?YES → Functional
Q2 Is it a quality / limit (fast, within X seconds, secure, 24/7, easy, reliable)?YES → NFR · Product
Q3 Is it a company rule / internal tool / language / process / standard of the organization?YES → NFR · Organizational
Q4 Is it a law / government / regulation / outside standard?YES → NFR · External

  • Functional = السيستم بيعمل إيه: فعل. «يطبع فاتورة»، «يعمل reports شهرية»، «يرجّع الباسورد بالإيميل»، «يوفّر للعميل آخر إصدار» ← كله Functional.
  • Non-Functional = بيعمله إزاي: صفة أو قيد. «بسرعة»، «في خلال ٣ ساعات»، «آمن»، «سهل» ← Non-Functional.
  • حيلة سهلة: شيل الصفة من الجملة. لو الجملة لسه ليها معنى كفعل ← FR. لو الجملة كلها عبارة عن الصفة أو القيد ← NFR. «يطبع فواتير بسرعة»: الـ FR = يطبع، والـ NFR = بسرعة.
  • أنواع الـ NFR ٣:
    • Product = جودة المنتج نفسه (السرعة، الاعتمادية، الأمان، سهولة الاستخدام).
    • Organizational = قواعد الشركة من جوّه (البرامج اللي عندهم، لغة البرمجة، طريقة الدخول).
    • External = من برّه (قانون، حكومة، معايير صناعة).
  • ⚠️ سؤال الكويز المشهور: «must integrate with the existing accounting software used by the company» ← Organizational! الـ ChatGPT بيقول External وده غلط. البرنامج ده جوّه الشركة، يعني سياسة داخلية.
  • سؤال Mid 2025 B: «Upgrading the hardware should be done within 3 hours» ← NFR (قيد وقت).

3.4

Specification, SRS & Validation

الـ SRS، وبنتأكد من إيه في الـ validation

Requirements specification: writing down user and system requirements in a requirements document: clear, unambiguous, easy to understand, complete and consistent. Starting point for design; may be part of the contract.

The software requirements document = SRS (software requirements specification): the official statement of what is required of the system developers. Includes user requirements and system requirements. Created after the requirements are collected from stakeholders. Its level of detail depends on the system type and process.

Requirements validation: customers and developers read the document in detail and check for errors, ambiguities and inconsistencies, then negotiate fixes. Check (V-C-C-R):

  • Validity: does it provide the functions that best support the customer's needs?
  • Consistency: any requirement conflicts?
  • Completeness: are all required functions included?
  • Realism: can it be implemented with the available budget and technology?

Validation techniques: requirements reviews (systematic manual analysis) · prototyping (an executable model to check requirements).

عالشرح بالعربيSRS = العقد الرسمي
  • الـ SRS = الوثيقة الرسمية للمتطلبات. «also called» ← SRS. وبتتعمل بعد جمع المتطلبات (Mid 2025 B: True).
  • Validation بيتشيّك على ٤ «V-C-C-R»: Validity · Consistency · Completeness · Realism. والكويز: «validation checks for» ← validity, consistency, completeness, realism.
  • Realism = ينفع يتعمل بالميزانية دي؟ مش «عايز Netflix بـ ٥٠٠ جنيه» 😂.

4.2

Use Case Elements: Actors, Use Cases, Boundary

الرموز الأساسية، والـ primary والـ secondary

Use case modelling supports requirements elicitation: it describes what a user expects from a system, from the user's perspective. A discussion tool and common language between developer and user. Use case diagrams show interactions between:

Actoranyone or anything outside the system that interacts with it: human (Student) or non-human (E-mail Server); individual, group, company
Use caseUse casewhat the system should do; an ellipse with the name inside (most common notation); name = verb + noun

Use case diagrams don't show the order in which use cases execute and are implementation-independent. More detail is given by a textual flow of events, a structured table, or a sequence diagram.

4.3

The 4 Relationships: Association, Include, Extend, Generalization

أهم حاجة في الرسمة: الأسهم رايحة فين

RelationshipBetweenNotationMeaning
Associationactor ↔ use case onlysolid line, no arrowthe actor participates in the use case
«include»use case → use casedashed arrow from base → includedthe base always uses the included behaviour; extract common behaviour shared by 2+ use cases into a new use case
«extend»use case → use casedashed arrow from extending → base + note with conditionadds optional or conditional behaviour at extension points; base is meaningful on its own
Generalizationactors (and sometimes use cases)solid line, hollow triangle at the parent"is a": the child inherits all use cases / relationships of the parent

Only two relationships are allowed between use cases: include and extend (plus generalization sometimes). Elements that may be generalized: use cases and actors.

  • Extend rules: the extending use case depends on the base · is usually optional · the base must be meaningful on its own · add a condition in a note.
  • Actor generalization: sub-actor Y inherits from super-actor X → Y takes part in all use cases of X. Multiple inheritance allowed. An {abstract} super-actor groups common properties: Professor OR Assistant can query student data (vs two associations = both needed together).
  • Use case generalization: B inherits A's behaviour (may extend or overwrite it) and all of A's relationships. A may be {abstract}: not executable directly, only B is.
«include»Base - - - -▷ Included"I always need you"
«extend»Extra - - - -▷ Base"I sometimes add to you"
GeneralizationChild ────▷ Parent"I am a kind of you"
عالشرح بالعربيInclude = دايمًا · Extend = أحيانًا · Generalization = is a
  • Association = خط عادي بين actor و use case بس. ماتحطش association بين use case و use case!
  • «include» = لازم كل مرة. «Withdraw» لازم يعمل «Authenticate». السهم من الأساسي للمضمّن (من Withdraw لـ Authenticate). زي «الأكل» include «تغسل إيدك» 🧼.
  • «extend» = أحيانًا، بشرط. «Print Receipt» بتحصل بس لو عايز. السهم من الإضافي للأساسي (من Print Receipt لـ Withdraw)، عكس الـ include! وحط note فيها الشرط. زي «الأكل» extended by «الحلو»: لو لسه فيه مكان 🍰.
  • Generalization = «is a». «Member is a Visitor» ← خط بـمثلث فاضي عند الأب (Visitor). والابن بيورث كل حاجة الأب بيعملها، فماتكرّرش الخطوط.
  • أسئلة MCQ: «include purpose» ← extract common behavior · «extend used when» ← additional behavior under certain conditions · «actors share similar responsibilities» ← generalization · «may be generalized» ← use cases and actors.
🔁
الطالب: بيرسم سهم الـ extend من الأساسي للإضافيالدكتورة: 🖊️❌ «extend يا حبيبي السهم بيرجع للـ base»
فخ: «Include → adds optional behavior» ← غلط (ده extend). «Extend → always executed» ← غلط. الصح: Extend → adds conditional behavior to base case.
4.4

How to Draw It: the 7-Step Recipe

الطريقة اللي تخلّيك تجيب الـ ٦ درجات

1
Read & underline

علّم على الأسماء (actors) والأفعال (use cases) في السؤال. كل «can + verb» = use case.

2
Draw the system boundary

مستطيل كبير، واكتب اسم السيستم فوق جوّاه. سيب مكان على الشمال واليمين للـ actors.

3
Place the actors outside

الـ primary على الشمال، والـ secondary (assists / helps / external system) على اليمين. الـ actor اللي «is a» actor تاني تحته على طول.

4
Add use cases inside

بيضاوي لكل فعل، والاسم Verb + Noun (Borrow Book). رتّبهم جنب الـ actor بتاعهم.

5
Associations

خط عادي من كل actor لـ use cases بتاعته. ماتوصّلش الابن بحاجات الأب، هو بيورثها.

6
Generalization

كل «X is a Y» ← خط بمثلث فاضي عند Y.

7
«include» + «extend» (the note asks for them!)

ضيف use case جديدة مشتركة (Log In / Authenticate / Validate / Update Balance) بـ include، وواحدة اختيارية بشرط بـ extend + note. السؤال بيقول «at least once» ← حط واحدة من كل نوع.

✅ Checklist قبل ما تسلّم
  • اسم السيستم مكتوب في المستطيل؟
  • كل الـ actors برّه وكل الـ use cases جوّه؟
  • أسماء الـ use cases فعل + اسم؟
  • مفيش association بين use case و use case؟
  • الـ include: السهم من الأساسي. والـ extend: السهم للأساسي + note بالشرط؟
  • مثلث الـ generalization فاضي وعند الأب؟
  • مكتوب «include» و «extend» بين أقواس « » على الأسهم المتقطعة؟
عالشرح بالعربيأشهر ٦ غلطات بتخسّرك درجات
  • ❌ تحط actor جوّه المستطيل.
  • ❌ توصّل use case بـ use case بخط عادي (لازم include أو extend).
  • ❌ تعكس سهم الـ extend.
  • ❌ تعكس مثلث الـ generalization (المثلث عند الأب مش الابن).
  • ❌ ترسم أسهم ترتيب بين الـ use cases كأنها flowchart.
  • ❌ تنسى الـ include/extend مع إن السؤال طالبهم «at least once».
ملحوظة الدكتورة: الإجابة النموذجية بتقول «Answers might vary»، يعني أي use case معقولة للـ include/extend مقبولة، طالما الرموز والاتجاهات صح.

Virtual Learning Environment

  • The main actor is a user who can only search content and create a membership.

  • A moderator is a member that can add content, delete content, and manage member accounts.
Mid 2024 B · 5 marks

Banking System

  • The main actor is a customer who can open an account, deposit funds, and withdraw funds.
  • A Bank Employee can assist with account-related services.
  • A non-resident foreign customer (NRFC) is a customer that can convert currency.
PRACTICE · exam level

Hotel Reservation System

  • A Guest can make and cancel reservations. A Receptionist checks guests in and out and can also make reservations.
  • A VIP Guest is a Guest who can request a room upgrade.
  • Payment at check-out is processed by an external Payment System. Cancelling less than 3 days before check-in adds a fee.
PRACTICE · exam level

Online Shopping System

  • A Guest can browse products and register. A Registered Customer is a Guest who can add to cart, checkout and track orders.
  • An Admin manages products. Checkout requires payment through an external Payment Gateway; a coupon may optionally be applied.
PRACTICE · exam level

ATM System

  • A Customer can withdraw cash, check balance and transfer funds; every operation needs PIN authentication verified by the Bank System.
  • A Technician refills cash. The customer may ask for a printed receipt after withdrawing.

Lecture 1 in 6 lines
  • Software = programs + documentation
  • Attributes M-D-E-A: maintainability · dependability · efficiency · acceptability
  • Generic (market) vs customized (one customer, contract)
  • Process: specification · design & implementation · validation · evolution
  • Challenges H-D-T · costs 60% dev / 40% test
  • Ethics C-C-I-C · ACM/IEEE = 8 principles
Process models
  • Waterfall: plan-driven, distinct phases · use when reqs clear + stable + time OK
  • Incremental: + cheaper change · faster delivery · easy feedback · − not visible · structure degrades
  • Reuse: COTS · + cost, speed · − compromises, loss of control
  • Avoidance (prototype) vs tolerance (incremental)
Agile
  • Principles: customer · incremental · people · embrace change · simplicity
  • XP: builds daily · delivery every 2 weeks · all tests pass
  • Story: As a… I want… So that…
  • Refactoring = improve structure, same behaviour · pair = 2 at 1 PC
  • Scrum: sprint 2–4 weeks · backlog · Scrum master = facilitator
Requirements
  • FR = what (verb) · NFR = how (quality/limit)
  • NFR P-O-E: product · organizational · external
  • User (natural language, what) vs system (detailed, how)
  • Feasibility → elicitation → specification → validation
  • Interview · scenario · ethnography · use case
  • SRS · validation V-C-C-R

قايمة الفخاخ 🪤
  1. Dependability = easy to modify → No, maintainability.
  2. Generic products are for a specific customer → False.
  3. Batch processing is real-time → False.
  4. Waterfall allows frequent changes → False.
  5. Waterfall is difficult to manage → No, easy to manage.
  6. Reuse gives total control over evolution → No, loss of control.
  7. "Use MySQL" is functional → No, NFR.
  8. "Integrate with the company's accounting software" is external → No, organizational.
  9. Consistent = no repetitions → No, no contradictions.
  10. Ethnography finds new features → No.
  11. Actors are always humans → No.
  12. Use case diagrams show order → No.
  13. Include = optional → No, extend is.
  14. Extend arrow points from base → No, it points to the base.
  15. Association between two use cases → Never.
  16. Fork follows only one path → False.
